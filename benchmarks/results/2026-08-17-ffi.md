# Released Polyglot FFI comparison: 2026-08-17

Host: AMD Ryzen 5 3450U with Radeon Vega Mobile Gfx (4 cores / 8 threads),
Linux 7.0.0-29-generic x86-64.

The Golyglot measurements used Go 1.25.1 at commit `5a7e7deb04da` plus the
current uncommitted compatibility and performance work. Both implementations
were pinned to CPU 0. Golyglot was compiled once and run with `GOMAXPROCS=1`:

```sh
CGO_ENABLED=0 go test -c -o /tmp/golyglot-bench.test ./benchmarks
GOMAXPROCS=1 taskset -c 0 /tmp/golyglot-bench.test \
  -test.run '^$' -test.bench . -test.benchmem \
  -test.count=5 -test.benchtime=1s
```

The Polyglot measurements used the Linux x86-64 shared library from the
v0.9.1 GitHub release. The downloaded archive had SHA-256
`1b83ab550997f44ea270c0f73c591a1b33d6168dffc25745ead59002d49d57a3`:

```sh
make fetch-polyglot-ffi
taskset -c 0 make bench-polyglot-ffi
```

Each value below is the median of five approximately one-second samples. All
cases use the same SQL input bytes and dialect path in both implementations.
Lower is better; the factor compares the slower median with the faster one.

| Operation | Case | Golyglot | Polyglot FFI v0.9.1 | Faster |
| --- | --- | ---: | ---: | ---: |
| Parse | simple | 7.960 µs/op | 11.078 µs/op | Golyglot 1.39x |
| Parse | medium | 41.597 µs/op | 69.532 µs/op | Golyglot 1.67x |
| Parse | complex | 162.627 µs/op | 278.459 µs/op | Golyglot 1.71x |
| Transpile | simple | 10.942 µs/op | 31.397 µs/op | Golyglot 2.87x |
| Transpile | medium | 59.539 µs/op | 162.151 µs/op | Golyglot 2.72x |
| Transpile | complex | 126.487 µs/op | 419.737 µs/op | Golyglot 3.32x |
| Format | simple | 8.783 µs/op | 12.408 µs/op | Golyglot 1.41x |
| Format | medium | 50.903 µs/op | 89.845 µs/op | Golyglot 1.77x |
| Format | complex | 121.845 µs/op | 229.530 µs/op | Golyglot 1.88x |

The FFI harness measures the public C ABI end to end: the foreign call,
Polyglot's JSON serialization and result allocation, status checking, and
`polyglot_free_result`. It does not decode the returned JSON in the caller.
The parse comparison is therefore not a parser-core microbenchmark: Golyglot
returns an in-memory Go AST, while the Polyglot FFI returns a serialized JSON
AST. Format and transpile are closer end-to-end comparisons, although their
return representations still differ.

## Exact-match fixture transpilation set

The expanded comparison resolves 12 cases directly from
`benchmarks/fixture_cases.json`. An untimed preflight verified that both the
final Golyglot binary and released Polyglot v0.9.1 produced each fixture's
exact expected output. Timings use the same CPU-0, five one-second sample
protocol as the synthetic cases.

| Case | Dialect path | Golyglot | Polyglot FFI v0.9.1 | Faster |
| --- | --- | ---: | ---: | ---: |
| PostgreSQL `MAKE_INTERVAL` | PostgreSQL -> MySQL | 15.152 µs/op | 45.289 µs/op | Golyglot 2.99x |
| PostgreSQL `UPDATE FROM` | PostgreSQL -> MySQL | 10.185 µs/op | 47.573 µs/op | Golyglot 4.67x |
| BigQuery timestamp truncation | BigQuery -> DuckDB | 41.190 µs/op | 122.345 µs/op | Golyglot 2.97x |
| DuckDB filtered aggregate | DuckDB -> Snowflake | 35.214 µs/op | 122.453 µs/op | Golyglot 3.48x |
| MySQL dynamic `DATE_ADD` | MySQL -> PostgreSQL | 27.284 µs/op | 74.789 µs/op | Golyglot 2.74x |
| Presto nested `ROW` DDL | Presto -> DuckDB | 11.964 µs/op | 16.337 µs/op | Golyglot 1.37x |
| Hive nested `STRUCT` DDL | Hive -> Spark | 15.463 µs/op | 18.080 µs/op | Golyglot 1.17x |
| Spark `POSEXPLODE` | Spark -> BigQuery | 33.830 µs/op | 279.773 µs/op | Golyglot 8.27x |
| T-SQL `OUTER APPLY` | T-SQL -> Spark | 50.676 µs/op | 186.068 µs/op | Golyglot 3.67x |
| Snowflake JSON path | Snowflake -> PostgreSQL | 14.682 µs/op | 22.506 µs/op | Golyglot 1.53x |
| ClickHouse nullable interval | ClickHouse -> PostgreSQL | 16.202 µs/op | 25.562 µs/op | Golyglot 1.58x |
| Generic `QUALIFY` | Generic -> MySQL | 27.892 µs/op | 59.736 µs/op | Golyglot 2.14x |

Golyglot is faster in all 12 selected cases; the geometric mean of the
per-case Polyglot/Golyglot ratios is 2.61x. The Hive nested-struct result is
close enough to treat as approximately tied on this host.

This set is deliberately filtered to behavior both implementations share and
manually stratified by syntax feature. It is not corpus-weighted, and the FFI
numbers continue to include foreign-call, JSON serialization, and result
allocation/free overhead.

A focused five-second CPU profile of the initial Presto nested-row result
explained its outlier. `normalizeDuckDBRawStatement` accounted for 53.8%
cumulative CPU, `normalizeDuckDBNestedQueries` for 38.0%, and
`strings.ToUpper` for 48.0% (these cumulative figures overlap). A pure
`CREATE TABLE (...)` column list had already been handled by the dedicated
DDL normalizer, but was then sent through the general raw-statement normalizer,
which recursively treated every nested type parameter list as possible SQL.

The target transformer now skips only that redundant second pass, based on
the original create-table tail; CTAS and clause-bearing tails retain the raw
normalizer. The Presto case fell from 37.189 to 11.964 µs/op (-67.8%), from
8,864 to 4,064 B/op, and from 104 to 27 allocations/op. It changed from a
2.28x Polyglot win to a 1.37x Golyglot win without cloning a DuckDB generator
or creating a parallel transformation path.

## Performance-cleanup effect

The pre-cleanup and post-cleanup binaries were also alternated on CPU 0 for
three one-second samples per case. The exact allocation counts improved in
all nine cases:

| Operation | Case | Before | After | Reduction |
| --- | --- | ---: | ---: | ---: |
| Parse | simple | 34 allocs/op | 28 allocs/op | 17.6% |
| Parse | medium | 147 allocs/op | 131 allocs/op | 10.9% |
| Parse | complex | 507 allocs/op | 454 allocs/op | 10.5% |
| Transpile | simple | 39 allocs/op | 33 allocs/op | 15.4% |
| Transpile | medium | 198 allocs/op | 170 allocs/op | 14.1% |
| Transpile | complex | 420 allocs/op | 362 allocs/op | 13.8% |
| Format | simple | 39 allocs/op | 33 allocs/op | 15.4% |
| Format | medium | 200 allocs/op | 184 allocs/op | 8.0% |
| Format | complex | 434 allocs/op | 403 allocs/op | 7.1% |

Median wall time improved by up to 11% in that alternating run. The two
smallest cases moved by less than 3%, which is within the host's run-to-run
noise. At that checkpoint, allocation counts and bytes had returned to the
clean `HEAD` baseline, while the expanded compatibility code still added
CPU-only overhead.

A second optimization phase was implemented conservatively after the initial
pinned comparison. PostgreSQL-to-MySQL source-function normalization now
shares the target transformation traversal, and lexer tokens carry a compact
canonical word ID for hot parser boundary checks. Those two changes left
allocation counts unchanged.

That intermediate binary was rerun with the same five-sample, CPU-0 protocol.
Relative to the preceding pinned binary, medians changed as follows (negative
is faster):

| Operation | Case | Before | Intermediate | Change |
| --- | --- | ---: | ---: | ---: |
| Parse | simple | 8.949 µs/op | 8.224 µs/op | -8.1% |
| Parse | medium | 53.243 µs/op | 49.616 µs/op | -6.8% |
| Parse | complex | 221.451 µs/op | 209.603 µs/op | -5.4% |
| Transpile | simple | 13.040 µs/op | 11.795 µs/op | -9.5% |
| Transpile | medium | 79.851 µs/op | 66.892 µs/op | -16.2% |
| Transpile | complex | 167.416 µs/op | 153.612 µs/op | -8.2% |
| Format | simple | 10.535 µs/op | 9.642 µs/op | -8.5% |
| Format | medium | 62.062 µs/op | 60.431 µs/op | -2.6% |
| Format | complex | 155.336 µs/op | 144.034 µs/op | -7.3% |

The transformation-heavy cases show the clearest benefit from fusing the AST
walks; movements of only a few percent should still be treated as within the
host's observed run-to-run noise.

Target specialization was implemented as a shared transformer context that
selects source/target behavior once and carries it through the traversal. No
per-dialect transformer or generator was cloned: the rule implementation and
generation path remain shared, avoiding the maintenance cost of parallel
dialect-specific code paths.

A final profile-backed phase made three lexer/DDL changes:

- the already-normalized pure DuckDB create-table column list no longer enters
  the general raw-statement normalizer;
- an allocation-free, case-insensitive word lookup now classifies keywords and
  returns parser word IDs in one pass; and
- numeric-prefix detection checks the two `0x`/`0X` bytes directly, while the
  lexer uses an ASCII fast path and retains its Unicode fallback.

generation, and dialect normalization are distributed, so broader changes
would need workload-specific evidence rather than another local cleanup.
